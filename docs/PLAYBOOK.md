# 个人开源维护手册

## 1. 仓库分工

| 类型 | 管理方式 |
| --- | --- |
| 个人主页 `shanghe000` | 展示真实可访问的精选原创项目，保持链接与状态准确 |
| 默认规范 `.github` | 统一贡献说明、Issue 表单、PR 模板与维护习惯 |
| 模板 `open-source-starter` | 新项目的文档、检查和发布起点 |
| 原创项目 | 一个仓库解决一个明确问题；README 说明用途、运行方式、限制与许可 |
| Fork | 保留上游来源与许可证，按实际需要同步；不计作原创成果 |
| 私有项目 | 先整理再决定是否公开，公开前单独审查历史、授权与配置 |

命名使用简短的 `lowercase-kebab-case`。已有仓库保持原名，避免破坏克隆地址和外部引用。

## 2. 创建项目

在 `open-source-starter` 页面选择 **Use this template → Create a new repository**。
或在模板的本地目录运行：

```sh
python3 scripts/new_project.py my-project --description "一句话说明解决什么问题" --visibility public
```

脚本创建仓库、复制模板并修改 README 标题，保留 GitHub CLI 当前登录身份；默认私有，公开需要明确选择。
它不修改本机全局 Git 身份。首次提交后按模板 README 执行仓库设置脚本。

开始编码前完成：

- README：解决的问题、适用对象、安装与最小示例、当前状态、截图或演示、限制。
- 许可证：新模板使用 MIT；复用第三方内容时保留其要求。既有项目缺许可证时单独决定，不自动补许可。
- 配置：只提交示例；本地配置与凭据进入忽略清单。
- 仓库 About：一句话简介与 3–6 个准确的主题；有真实演示地址再填 Website。
- 在 `Repository quality` 之外增加对应技术栈的真实测试、构建工作流。

## 3. 日常开发

```text
Issue / 明确的问题 → feature 分支 → 小范围 PR → 自动检查 → 审查 → squash 合并
```

个人项目无需强制另一位审批人；重要变更仍走 PR，保留动机和验证记录。
发布前查看 Actions 结果。现有成熟项目的测试流程优先，不用模板中的通用检查代替业务测试。

## 4. 发布

在新模板项目的 Actions 中手动运行 **Draft release**，输入如 `v0.1.0` 的版本号。
流程只允许默认分支，先运行仓库检查，再对该次运行的确切提交创建标签和 Release 草稿，并从合并记录生成说明。
检查草稿中的变更、兼容性、已知问题及安装说明后，再手动发布。
本流程不自动构建二进制或发布软件包；有此需要时加入项目自己的构建和制品上传步骤。
相同版本已存在时流程拒绝覆盖，应选择新版本或人工检查原草稿。

## 5. 每周维护（约 15 分钟）

1. 查看 `.github` 的 Repository audit 报告，优先补缺少的用途说明、许可证决策和运行指引。
2. 处理可复现 Bug 与必要的依赖更新；合并前检查变更和运行结果。
3. 对长期未维护的项目写明状态；归档、删除、重命名或改变可见性单独决定。
4. 新项目达到可用状态后更新主页精选区与 GitHub 置顶项目。

每月查看一次 Fork 是否仍有价值，以及上游是否有需要的修复；不自动将上游更新合入个人修改。

## 6. 分支与权限

新模板提供 `scripts/configure_repository.py`，用于设置 squash 合并、合并后删除功能分支、私密漏洞报告和默认分支规则。
规则要求 PR、`Repository quality` 检查和讨论已解决，阻止默认分支删除与强制覆盖，不强制外部审批。
仓库管理员可在 PR 中绕过规则，日常应等待检查通过。规则和仓库设置不随模板自动复制。
默认只为公开仓库配置规则；私有仓库可能需要付费计划，脚本不会假装已启用。

## 7. 现有仓库的接入顺序

先完善公开原创工具的说明与许可，再接入与其技术栈相符的检查；实验项目写清边界。
学习仓库保留真实状态，只有 README 的项目不包装成已实现的框架。
公开仓库缺许可证并不等于已经授予开源使用许可。
